<objective>
Replace the single Base64 image column on all four image-bearing entities (Character, GlobalCharacter, Location, GlobalLocation) with dual `OriginalImageData` + `CroppedImageData` `byte[]` (Postgres `bytea`) columns, migrating existing data in-place, and introduce the `HasImage` read flag + the image write contract that lets image bytes travel through the existing session-upsert and Global* create/update JSON paths without clobbering stored bytes on unrelated saves.

This is the atomic backend data-model foundation for Phase 4 (IMG-01, IMG-02, IMG-03, IMG-05). It is a single coordinated rename: every reference to `PortraitBase64`/`ImageBase64`/`PortraitPanX`/`PortraitPanY` must change together so the solution stays build-green in one commit.

Purpose: Establish the storage model every later Phase 4 plan reads and writes through (binary endpoints in Plan 03, crop-write wiring in Plan 04, display refactor in Plan 05).
Output: Migrated schema, updated entities/DTOs/services/repositories, and an integration test proving migration data-preservation + the fallback-read + write-contract behavior.

**Phase user story (derived from ROADMAP Phase 4 Goal):** As a DM, I want to crop portrait and location images end-to-end with a Cropper.js v2 tool (zoom, EXIF-safe, touch) and have both the original and cropped versions stored and served from fast cached endpoints, so that I can re-crop without re-uploading, animated GIFs still display, and my character/location pages load without waiting on image bytes.
</objective>

<image_write_contract>
The single design decision resolving RESEARCH Open Question #1 (session-scoped CharacterDto/LocationDto are bidirectional). Adopt **Option B** (single bidirectional DTO for Character/Location, separate read/write DTOs for Global*), with this exact write contract applied wherever incoming image fields are copied onto a stored entity:

Given the incoming write carries `HasImage` (bool), `OriginalImageData` (byte[]?), `CroppedImageData` (byte[]?):
1. `HasImage == false` -> clear both: stored `OriginalImageData = null`, stored `CroppedImageData = null`.
2. `HasImage == true` AND `OriginalImageData != null` -> full replace: stored `OriginalImageData = incoming.OriginalImageData`; stored `CroppedImageData = incoming.CroppedImageData` (may be null, e.g. a GIF replacing a previously-cropped image — this correctly clears the stale crop).
3. `HasImage == true` AND `OriginalImageData == null` AND `CroppedImageData != null` -> re-crop: stored `CroppedImageData = incoming.CroppedImageData`; stored `OriginalImageData` left unchanged (IMG-02: re-crop without re-upload).
4. `HasImage == true` AND both null -> no-op: preserve stored original + cropped (the common case for a save that only touched other fields).

Read side: services set `HasImage = (entity.OriginalImageData != null)` and leave the DTO byte fields `null` (bytes are never serialized into read responses — IMG-05).
</image_write_contract>
