## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Trusting executor-reported `expected_base` in `<worktree_metadata>` | Each `gsd-executor` agent's returned `<worktree_metadata>` block includes an `expected_base` field, but in practice this reports the agent's OWN final branch-tip commit (the SHA after all its own commits), not the SHA the branch actually forked from. Recording this value directly into the wave manifest via `worktree.record-agent --base <this value>` causes `worktree.cleanup-wave` to fail with `reason: "base_mismatch"` even though the branch is perfectly mergeable. Hit this twice in Wave 1 (both 04-01 and 04-02). | blocking | Before calling `worktree.record-agent`, always independently compute `git merge-base <worktree-agent-branch> <target-branch>` (e.g. `feature/gsd-introduction`) and use THAT value as `--base`, not the executor's self-reported `expected_base`. If `worktree.record-agent` refuses a re-record with `duplicate_entry` (it dedups on worktree_path+branch and won't overwrite), edit the manifest JSON file directly with the corrected value — it's orchestrator-owned bookkeeping, not git state, so direct editing is safe. Also note: on this Windows/Git-Bash setup, `/tmp/...` paths written via the `Write` tool did NOT land in the same file `bash`/`gsd-tools` resolved via `${TMPDIR:-/tmp}` (a short-name vs long-name profile-path mismatch: `TC541~1.SCH` vs `t.schut`) — use a `bash` heredoc (`cat > "/tmp/file" << 'EOF' ... EOF`) to edit the manifest instead of the Write tool, so the edit lands where `gsd_run` actually reads from. |
| `worktree.cleanup-wave` has zero tolerance for file deletions | The automated merge/cleanup helper (`gsd-tools query worktree.cleanup-wave`) checks `git diff --diff-filter=D --name-only HEAD...<branch>` and unconditionally blocks (`reason: "branch_contains_deletions"`) if the branch deletes ANY file relative to current HEAD — there is no override flag or config knob in `worktree-safety.cjs`. This is by design (deletions are the highest-risk thing to silently auto-merge), but it means any plan whose `files_modified` includes a legitimate, intentional deletion (04-02 deleted `PortraitCrop.jsx` per D-10; 04-06 will delete `CropModal.jsx`) cannot go through the automated tool. | blocking | For a worktree branch containing an intentional deletion: (1) verify the deletion is expected (cross-check against the plan's `<action>` text — 04-06's plan explicitly says to delete `CropModal.jsx` after its last importers are removed), (2) skip `worktree.cleanup-wave` for that specific entry, (3) merge manually: `git merge --no-ff <branch> -m "chore: merge executor worktree (<branch>)"`, then `git worktree remove <path> --force` and `git branch -D <branch>`. Process any OTHER same-wave plans without deletions through the automated tool first (put them in their own single-entry manifest), then handle the deletion-containing one manually last. |
| Generic post-merge build/test sniff misses one stack in a mixed-language repo | `execute-phase/steps/post-merge-gate.md`'s auto-detect logic picks ONE build/test command by checking `Makefile` → `Justfile` → `Cargo.toml` → `go.mod` → `package.json`, in that priority order. Since `package.json` exists in this repo, the generic sniff would run `npm run build`/`npm test` ONLY, completely skipping the `.NET` solution — exactly the side Waves 1 and 2 touched most heavily (EF migration, endpoints, services). | advisory | Continue running both stacks explicitly after every wave's merge: `dotnet build Omphalos.slnx` (note: `.slnx`, not `.sln`), `dotnet test` (requires Docker for `Omphalos.IntegrationTests`, confirmed available), and `npm run build`. Do this for Wave 3 and Wave 4 too. |
