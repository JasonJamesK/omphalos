<objective>
Deliver PERSIST-04/D-03: a visible save-failure indicator. Today, a failed session save is swallowed by `.catch(() => {})` in `AppContext.jsx` — the UI shows the edit as applied while the server never received it. This plan wires the existing `db.saveSession` rejection to a new `saveError` reducer field and renders the `SaveFailureToast.jsx` component exactly per the approved `01-UI-SPEC.md` contract.

Purpose: Silent save failure directly violates the core value ("...without losing content"). The DM must be told when a change didn't persist. No new state library or toast dependency is added — a single `saveError` field on the existing `useReducer` store is sufficient (RESEARCH.md Pattern 3), matching every other component's `useApp()` read/dispatch pattern.

Output: `saveError` state + `SAVE_FAILED`/`CLEAR_SAVE_ERROR` actions in `AppContext.jsx`, the `saveSession` catch wired to dispatch `SAVE_FAILED`, a new `SaveFailureToast.jsx`, and its single mount in `App.jsx`. Also adds an anti-regression comment at the `UPDATE_SESSION` reducer case (this plan owns `AppContext.jsx`).
</objective>

| T-01-02 | Information Disclosure | SaveFailureToast copy | medium | mitigate | The `saveSession` catch discards the Error argument and dispatches a boolean payload; the toast renders fixed copy ("Your last change wasn't saved...") from `01-UI-SPEC.md`, never the raw `Error` message/stack. Do not "improve" it to surface exception text. |
| T-01-05 | Denial of Service (UX) | Toast stacking on repeated failures | low | accept | A single `saveError` field naturally collapses multiple failures into one replace-in-place toast (UI-SPEC "Multiple failures: replace, don't stack"); no queue/list is introduced, so no unbounded-toast growth is possible. |
