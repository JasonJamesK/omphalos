## Design System

| Property | Value |
|----------|-------|

**shadcn gate note:** No `components.json` exists (confirmed by direct check — absent from repo root). This matches Phase 2's finding and decision: the project has a mature, fully hand-rolled Tailwind + custom-CSS dark theme (`CLAUDE.md` "Styling conventions"), and this phase introduces **zero new components** — it is pure integration of the already-shipped `MarkdownField` (Phase 2) into 4 new call sites. **Component reuse note:** This phase adds **no new component files**. `MarkdownField.jsx`, `MarkdownPreview.jsx`, and `markdownToolbar.js` (all built in Phase 2, already in production at 6 usage sites) are wired in unchanged at 4 new locations, satisfying MDED-09. The only possible code change to `MarkdownField.jsx` itself is one additive, optional `bare` prop (see Callout integration below) — everything else in this contract governs how the *existing* component's chrome sits inside Session Prep's denser, nested block layout, not new visual design.

## Spacing Scale

Declared values (must be multiples of 4), unchanged from Phase 2 — this phase adds no new spacing tokens:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Toolbar button vertical padding (`py-1`) |
| sm | 8px | Toolbar button horizontal padding (`px-2`), gap between toolbar button groups, block-internal vertical rhythm (`space-y-1.5`/`space-y-2` in `LootBlock.jsx`/`PhaseCard.jsx`) |
| md | 16px | Split-view editor/preview column gap (inherited from `.markdown-field-body` grid, `index.css` line 82); vertical spacing between top-level `SessionPrep.jsx` sections (`space-y-4`) |
| lg | 24px | Not used by this phase's markdown wiring |
| xl | 32px | Not used by this phase's markdown wiring |
| 2xl | 48px | Not used by this phase's markdown wiring |
| 3xl | 64px | Not used by this phase's markdown wiring |

Exceptions:
- **Container-query breakpoint: 480px** (unchanged, already shipped in `index.css` line 64/81 — no new CSS). Per `03-RESEARCH.md`'s width analysis, all 4 of this phase's call sites (Overview & Hook, Notes, Callout, Loot description) sit in a full-width page tab with no `max-width` constraint anywhere in the layout chain (`App.jsx` → `SessionPrep.jsx` → `PhaseCard.jsx` → block component), so container widths are typically 500px+ on any normal desktop viewport. **Side-by-side split view is the expected default for all 4 fields on desktop** — tab-toggle is the narrow-viewport fallback only, not the primary design target (unlike Phase 2's ~330px character-field columns, where tab-toggle was common).
- **No `max-height`/internal scroll on any field** (unchanged from Phase 2, D-10 carries forward) — the containing page tab already scrolls (`flex-1 overflow-y-auto`, `App.jsx` line 134).
- **Loot item row spacing (`bg-[#161310] rounded p-2`, existing) is unchanged** — `MarkdownField`'s own `#161310` background matches the loot-item row's background, so nesting does not create a visible seam beyond the field's own border.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#161310` | Page background; `<textarea>` background at all 4 sites; Loot item row background (unchanged, matches `MarkdownField`'s own background so nesting shows no seam) |
| Secondary (30%) | `#211b17` | Toolbar bar background, tab-strip background (unchanged from Phase 2) |
| Accent (10%) | `#d4a574` | See "Accent reserved for" below |
| Destructive | `#b24545` | Loot item's existing `×` remove button only (pre-existing, unchanged by this phase — no new destructive control introduced) |

Accent reserved for:
- Markdown preview heading text color (`h1`/`h2`/`h3`) at all 4 new sites
- Active/toggled toolbar button background + text (`bg-[#d4a574] text-[#161310]`)
- Active tab indicator in narrow/tab-toggle mode
- `<textarea>` focus border (`focus:border-[#d4a574]`)
- "+ New Phase" button (pre-existing, `SessionPrep.jsx` — unchanged, not part of this phase's new surface but stays in the accent budget)

**Callout variant color is explicitly NOT accent-budget territory:** `CalloutBlock`'s `borderLeft` color (`#d4a574` for Flavor Text, `#6b8e6b` green for Read-Aloud) is a **semantic state color** distinguishing two content types, not a UI accent — it must remain on the outer wrapper `<div>` exactly as today. Flavor Text's border happens to reuse the same hex as the app's accent color, but its role here is semantic (content-type marker), not decorative-accent; do not let this coincidence justify moving it elsewhere or diluting it into a generic accent treatment. Read-Aloud's green border is a second semantic color already established in this codebase (not "destructive" — it signals "read this to players," unrelated to danger/deletion) and is out of scope to change.

No other element in this phase's scope may use the accent color. `MarkdownField`'s inactive-toolbar-button state, borders, and body text all use neutral tokens (`#332922` borders, `#f0f0f0` primary text, `#999999` muted text) — unchanged from Phase 2.

## Component-Specific Integration Contracts

These sections resolve the two discretionary questions CONTEXT.md delegated (D-04, D-05) and lock in the required correctness fix identified in `03-RESEARCH.md`. They are binding for the plan and executor, not open questions.

### D-04 — Block chrome density (Notes, Callout, Loot description)

**Decision: full chrome everywhere, zero divergence.** Notes, Callout, and Loot's `MarkdownField` instances use the exact same toolbar + Edit/Preview-tabs chrome as Overview & Hook — no compact variant is built. Rationale (from `03-RESEARCH.md`): all 4 sites measure 500px+ container width on real desktop viewports (no `grid-cols-2` split anywhere in Session Prep, unlike Phase 2's modal forms), so the side-by-side layout is the common case at every site, not just Overview & Hook. Building a second "compact" skin would fork MDED-09's single-component requirement for a problem (visual crowding) that the measured container widths say will not actually occur. **Fallback only:** if visual QA during execution shows the toolbar+tabs genuinely overwhelms Loot's per-item row once built, the fix is to omit the "Markdown supported" hint caption at that one site (already anticipated in the Copywriting Contract above) — not to build a second component or a `compact` prop.

### D-05 — Callout visual identity integration

**Decision: Option A — drop forced italic, keep colored-left-border wrapper as outer chrome.**

1. Remove the `italic` Tailwind class from `CalloutBlock.jsx`'s textarea replacement entirely. Do not port it to `MarkdownField`'s `textareaClassName` prop, and do not add italic styling to `.markdown-preview`. The DM can type `*italics*` explicitly now that raw markdown syntax is available — forcing italic via CSS on the edit pane while the preview pane renders unstyled (`.markdown-preview em` is `font-style: italic; color: #d4d4d4` only when the DM actually writes `*text*`) would make the same text look different in Edit vs. Preview for no reason a DM would understand (Pitfall 2 in `03-RESEARCH.md`).
2. Keep `CalloutBlock`'s existing colored-left-border wrapper `<div>` (`borderLeft: 3px solid ${v.color}`, `backgroundColor: '#161310'`) as the outer chrome — it already carries the Flavor Text (amber `#d4a574`) vs. Read-Aloud (green `#6b8e6b`) distinction at a glance, and this affordance must survive (hard requirement from CONTEXT.md D-05).
3. `MarkdownField` is placed inside that wrapper using its default border/chrome unchanged — build this way first (zero `MarkdownField.jsx` changes). Both the wrapper and `MarkdownField` use `#161310` background, so no color clash; the result is a subtle nested-border "box in a box," which is an acceptable default per `03-RESEARCH.md`'s recommendation.
4. **Contingent, not default:** only if visual QA during execution judges the double border genuinely cluttered, add one additive `bare` prop to `MarkdownField.jsx` (default `false`, so every other Phase 2 call site stays pixel-identical) that drops `MarkdownField`'s own `border border-[#332922] rounded-lg` when `true`, and pass `bare` only from `CalloutBlock.jsx`. This keeps `MarkdownField` a single shared component (MDED-09) rather than forking a second one. Do not add this prop speculatively — build without it first.

### Loot list-key stability (required correctness fix, not a styling choice)

`LootBlock.jsx` currently keys its item list by array index (`key={i}`) and creates items with no `id` (`{ name: '', description: '' }`). Once `MarkdownField` — a stateful component holding its own `activeTab` and auto-grow height — is nested in this list, index-keying causes React to reuse a sibling item's `MarkdownField` instance (and its Edit/Preview tab state) across a delete/reorder, showing the wrong tab active for the wrong logical item (Pitfall 1, `03-RESEARCH.md`). This is in-scope, required plumbing for MDED-02's Loot wiring, not an optional polish item:

- Add a stable `id` on item creation using the existing `${type}-${Date.now()}-${Math.random().toString(36).slice(2)}` generator convention already used by `phaseUid()`/`blockUid()` in this codebase (e.g. `itemUid()`).
- Key the list by `item.id ?? i` (index fallback covers pre-existing persisted items created before this fix ships — display-time only, no data migration required).
- No visual change results from this fix — it is purely a React reconciliation correctness requirement that must land alongside the `MarkdownField` swap on `items[i].description`, otherwise the swap introduces a regression.
