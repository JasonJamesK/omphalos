  <action>
    Rewrite `markdownToolbar.js` so the two exported mutation functions edit the textarea through the browser's native editing pipeline instead of a wholesale `.value` assignment. Keep the module a dependency-free set of pure DOM helpers, keep the two public exports `wrapSelection(textareaRef, before, after = before)` and `insertAtCursor(textareaRef, text)` with unchanged signatures and call semantics (so `MarkdownField.jsx` needs no changes), and keep all four toolbar buttons producing byte-for-byte the same inserted markdown as before.

    Remove the `setNativeTextareaValue` helper entirely, including its use of the `HTMLTextAreaElement.prototype` `value` property-descriptor setter. That native-setter-plus-`dispatchEvent` approach is exactly what destroys the browser's native Ctrl+Z undo history (confirmed root cause) and must not remain anywhere in the module.

    Add one new internal helper — name it `applyRangeEdit(textarea, start, end, replacement, selectionStart, selectionEnd)` — that performs the edit and cursor restore for both public functions:
    - Guard against a null element.
    - Call `textarea.focus()` first (setRangeText and the undo entry require the field to be the active editing target).
    - Call `textarea.setRangeText(replacement, start, end, 'preserve')` to replace the `[start, end)` range with `replacement`. This routes the change through the browser's real text-editing pipeline, so it is recorded as a discrete, undoable step on the native undo stack — the behavior the old native setter destroyed.
    - Dispatch `new Event('input', { bubbles: true })` on the textarea after the edit. Retain this dispatch: `setRangeText` is not guaranteed by the HTML spec to emit an `input` event, and React's controlled `onChange` only fires when a native `input` event reaches the React root and the value tracker sees a change. This dispatch is a pure notification — it does NOT touch or clear the undo stack (only the removed wholesale `.value` assignment did that), so it preserves the undo fix while keeping React state in sync.
    - Restore the caret/selection to `[selectionStart, selectionEnd)` inside a `requestAnimationFrame` callback that re-focuses the element and calls `setSelectionRange` — mirroring the existing post-mutation cursor-restore timing so selection survives React's controlled re-render.

    Update `wrapSelection` to keep computing `start`/`end`/`selected` from the element's current selection exactly as today, then call `applyRangeEdit(el, start, end, before + selected + after, start + before.length, start + before.length + selected.length)` so the inserted markers stay outside the restored selection (identical selection result to the current implementation).

    Update `insertAtCursor` to keep computing `lineStart` from the current caret exactly as today, then call `applyRangeEdit(el, lineStart, lineStart, text, start + text.length, start + text.length)` — a zero-width range insertion at the line start with the caret restored `text.length` characters past its original position (identical to the current implementation).

    Comments: explain in plain language WHY setRangeText is used (native editing pipeline → undo-tracked) and WHY the input dispatch is retained (React controlled-value sync only). Per project CLAUDE.md, do NOT embed any phase/plan/requirement/decision identifiers in source comments, and do NOT describe the old native-value-setter pattern in a comment.
