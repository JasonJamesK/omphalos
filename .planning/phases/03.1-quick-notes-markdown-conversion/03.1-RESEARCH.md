## Summary

This phase has no new technology to evaluate. `MarkdownField`, `MarkdownPreview`, and `markdownToolbar.js` were built and hardened across Phase 2 and Phase 3, and all required packages (`react-markdown@10.1.0`, `remark-gfm@4.0.1`, `remark-breaks@4.0.0`, `strip-markdown@6.0.0`) are already installed in `package.json`. The work is: (1) add one opt-in boolean prop `forceTabs` to `MarkdownField.jsx` that adds a modifier class to its root div, (2) add three CSS rules to `index.css` that override the `@container` split-view behavior back to tabs-visible/single-pane when that modifier class is present, and (3) swap the Quick Notes `<textarea>` in `SessionLog.jsx` for `<MarkdownField forceTabs .../>`, updating the local `updateNotes` handler from an event-reading signature to a raw-string signature.

Three findings from direct code inspection matter for planning, beyond what UI-SPEC.md already worked out:

**First**, the CSS specificity math in CONTEXT.md/UI-SPEC.md is correct, verified against the actual current `index.css` (lines 63-85, not just the excerpt quoted in CONTEXT.md). `.markdown-field-tabs`, `.markdown-field-body`, and `.markdown-field-pane-hidden` are each single-class selectors (specificity 0,1,0) both at their base declaration (lines 65-66, 79) and inside the `@container mdfield (min-width: 480px)` block (lines 82-84). A new rule using a two-class compound selector like `.markdown-field-force-tabs .markdown-field-tabs` has specificity (0,2,0), which is strictly higher and therefore wins regardless of source order or whether it sits inside or outside the `@container` block. CSS's cascade only falls back to "source order" as a tie-breaker when specificity is *equal* — since (0,2,0) > (0,1,0) unconditionally, no `!important` and no duplication inside the `@container` block is needed. The three new rules can be placed anywhere after the base `.markdown-field-*` rules; UI-SPEC.md's suggested placement (immediately after the `@container` block, lines 81-85) is fine and reads clearly for future maintainers.

**Second**, `updateNotes(e)` in `SessionLog.jsx` (line 48) is used in exactly two places in the entire codebase: its own definition and the single `onChange={updateNotes}` call site being replaced (line 196). It is never passed as a prop to another component and never referenced elsewhere. Changing its signature from `(e) => ...e.target.value` to `(v) => ...v` is a fully isolated, safe change — no other caller needs updating.

**Third**, there is a second, independent write path into `session.sessionNotes` that this phase does not touch and must not break: `Toolkit.jsx`'s `SaveBtn` component (lines 99-114) dispatches `UPDATE_SESSION` directly with `sessionNotes: (activeSession.sessionNotes ? activeSession.sessionNotes + '\n' : '') + line`, where `line` is a timestamp-prefixed string like `[14:32] DC 15 STR check`. This is the mechanism behind the "DC button clicks are logged here automatically" caption already displayed above the field. It does not call `updateNotes` and is unaffected by the handler signature change. Its output (newline-joined, timestamp-prefixed plain-text lines) will render correctly through `MarkdownField`'s existing `remark-breaks` configuration (single `\n` renders as a line break, per MDED-06, already proven at every other `MarkdownField` site) — no special-casing needed, but worth flagging so the planner's verification step includes "click a DC button, confirm the auto-logged line still appears correctly in both Edit and Preview tabs of the new `MarkdownField`."

Also confirmed by direct read: dropping the current `font-mono text-xs` styling has zero downstream effect. `pdfExport.js`'s `addText()` (line 26) calls jsPDF's own `doc.text()`/`doc.splitTextToSize()` using jsPDF's font settings (`doc.setFontSize(9)`, no `doc.setFont('courier', ...)` anywhere in the file) — it reads `session.sessionNotes` as a raw string, completely independent of what CSS class the browser textarea used to render it. Likewise, `handleAISummary` in `SessionLog.jsx` (line 76) embeds `session.sessionNotes` as a raw string into an LLM prompt template — no fixed-width/alignment assumption exists in either consumer. The monospace font was purely a browser-editing cosmetic choice with no persisted or exported formatting dependency.

**Primary recommendation:** Implement exactly as UI-SPEC.md specifies — add `forceTabs` prop to `MarkdownField.jsx`, add the three CSS override rules to `index.css`, swap the Quick Notes call site, and change `updateNotes`'s signature to accept a raw string. No deviations needed; all of UI-SPEC.md's technical claims are verified correct against the live codebase.

### Pattern 1: Adding the `forceTabs` prop to `MarkdownField.jsx`

**What:** Add `forceTabs = false` to the destructured props and conditionally append a modifier class to the root div's `className`, matching the existing prop-default style already used for `className`, `textareaClassName`, `placeholder`, `autoFocus`.

**When to use:** Only inside `MarkdownField.jsx` itself; this is the one component-level change required by the phase.

**Example:**
```jsx
// Source: src/client/components/markdown/MarkdownField.jsx (current, verified by direct read)
// Before (line 18, 24):
export default function MarkdownField({ value, onChange, className = '', textareaClassName = '', placeholder = '', autoFocus = false }) {
  ...
  return (
    <div className={`markdown-field border border-[#332922] rounded-lg bg-[#161310] ${className}`}>

// After:
export default function MarkdownField({ value, onChange, className = '', textareaClassName = '', placeholder = '', autoFocus = false, forceTabs = false }) {
  ...
  return (
    <div className={`markdown-field ${forceTabs ? 'markdown-field-force-tabs' : ''} border border-[#332922] rounded-lg bg-[#161310] ${className}`}>
```
Default `false` means all 10 existing call sites (Phase 2's 6 + Phase 3's 4) are byte-for-byte unaffected — they never pass `forceTabs`, so the modifier class is never added for them.

### Pattern 2: The three CSS override rules

**What:** Three two-class compound selectors, each targeting one of the existing `@container`-driven rules, placed in `src/client/index.css` after the existing `@container mdfield (min-width: 480px)` block (line 85).

**Example:**
```css
/* Source: src/client/index.css (verified current content, lines 63-85) */
.markdown-field-force-tabs .markdown-field-tabs { display: flex; }
.markdown-field-force-tabs .markdown-field-body { display: flex; flex-direction: column; }
.markdown-field-force-tabs .markdown-field-pane-hidden { display: none; }
```

**Why this beats the `@container` block unconditionally:** Each of the three target rules — `.markdown-field-tabs`, `.markdown-field-body`, `.markdown-field-pane-hidden` — is a single-class selector, specificity (0,1,0), whether declared at the base level (lines 65-66, 79) or inside the `@container` block (lines 82-84; being inside an `@container`/`@media` at-rule does not add to selector specificity — at-rules only gate *whether* a rule applies, not its specificity once it does). The new override selectors are descendant compound selectors combining two classes (`.markdown-field-force-tabs` + `.markdown-field-tabs`, etc.), giving specificity (0,2,0). Per the CSS cascade algorithm, higher specificity always wins over lower specificity regardless of source order — source order is only a tie-breaker when specificity is *equal*. `[VERIFIED: direct read of src/client/index.css lines 63-85, cross-checked against the CSS Cascade and Specificity algorithm (W3C/MDN — selectors combined with a descendant/space combinator sum their individual specificities)]`. No `!important` is needed, and the rules do not need to be duplicated inside the `@container` block.

### Anti-Patterns to Avoid

- **Duplicating the override rules both outside and inside the `@container` block:** Unnecessary given the specificity math above — adds dead code a future reader has to reconcile.
- **Adding `!important` to the override rules:** Unnecessary and would make future overrides of this behavior (if ever needed) harder to reason about — specificity alone suffices here.
- **Porting `font-mono text-xs` into `textareaClassName`:** Directly contradicts D-03 (no other `MarkdownField` site uses this styling) and UI-SPEC.md's explicit resolution to drop it.
- **Adding a `checkpoint:human-verify` or migration step for the DC-button auto-log feature:** Not needed — `Toolkit.jsx`'s `SaveBtn` writes to the same underlying string field via the same `UPDATE_SESSION` dispatch; it requires no code change and is compatible with `MarkdownField`/`remark-breaks` rendering as-is. It only needs to be included in this phase's manual verification pass (see Validation Architecture).

## Common Pitfalls

### Pitfall 1: Assuming `updateNotes`'s signature change might break another caller

**What goes wrong:** A planner or reviewer might assume `updateNotes` needs to stay event-shaped because it's referenced elsewhere (e.g. passed as a prop to a child component), requiring an adapter/wrapper instead of a direct signature change.
**Why it happens:** Reasonable caution before any refactor of a shared handler.
**How to avoid:** Not applicable here — confirmed via `grep -n "updateNotes" src/client` that it appears in exactly two places (its own definition and the single `onChange={updateNotes}` JSX usage being replaced in this same phase). The signature change is fully isolated and safe.
**Warning signs:** None expected; if a future `grep` ever shows a third usage, re-evaluate before changing the signature.

### Pitfall 2: Assuming dropped monospace styling affects PDF export or AI summary formatting

**What goes wrong:** A planner or reviewer might think DC-roll-style content (e.g. `[14:32] DC 15 STR check — success`) needs fixed-width alignment preserved in the PDF export or the AI summary prompt, and therefore hesitate to drop `font-mono text-xs`.
**Why it happens:** The `font-mono` class currently applied to the browser `<textarea>` looks intentional/functional.
**How to avoid:** Confirmed via direct read of `src/client/utils/pdfExport.js` (`addText()`, lines 26-35) that PDF export renders `session.sessionNotes` through jsPDF's own font/size configuration (`doc.setFontSize(9)`, no monospace font ever set) — it consumes the raw string, not any DOM/CSS rendering. Likewise `SessionLog.jsx`'s `handleAISummary` (line 76-77) embeds the raw string into an LLM prompt with no width-alignment dependency. The monospace styling was a pure browser-editing cosmetic choice with zero persisted/exported formatting dependency — safe to drop per UI-SPEC.md.
**Warning signs:** None expected; if a future export format ever needs fixed-width rendering of DC-roll content, that would be a new, separate feature request, not something this phase's change threatens.

### Pitfall 3: Forgetting to verify the DC-button auto-log path still renders correctly through the new `MarkdownField`

**What goes wrong:** `Toolkit.jsx`'s `SaveBtn` (lines 99-114) appends timestamped lines directly to `session.sessionNotes` via its own `UPDATE_SESSION` dispatch, independent of `updateNotes`. This path is not touched by this phase's code changes but its *output* is now rendered through `MarkdownField` instead of a plain `<textarea>`.
**Why it happens:** Easy to overlook a second write path into the same field when focused on the primary `<textarea>` → `MarkdownField` swap.
**How to avoid:** No code change needed (already confirmed safe — `remark-breaks` already turns single `\n` into a visible line break, proven at every existing `MarkdownField` site per MDED-06). Just include it in manual verification: click a DC button in the Toolkit, confirm the auto-logged line appears correctly in both the Edit textarea and the Preview pane of the new Quick Notes `MarkdownField`.
**Warning signs:** If the appended line ever appeared run-together with prior content instead of on its own line, that would indicate a `remark-breaks` regression — not expected, since this phase doesn't touch the `MarkdownPreview` configuration.

### Pitfall 4: Misjudging the CSS specificity fix as needing `!important` or block duplication

**What goes wrong:** A less careful implementation might reflexively add `!important` to the override rules, or duplicate them inside the `@container` block "to be safe."
**Why it happens:** `@container`/`@media` blocks are sometimes mentally (incorrectly) associated with adding to specificity, or assumed to require matching specificity to override.
**How to avoid:** Confirmed via direct read of `index.css` and the CSS specificity algorithm: at-rules do not add specificity; they only gate whether a rule applies. A two-class compound selector (0,2,0) beats a single-class selector (0,1,0) unconditionally, regardless of source order or which side of an `@container` block it's declared on. Neither `!important` nor duplication is needed — implement exactly as Pattern 2 shows.
**Warning signs:** If the tab toggle mysteriously disappears at container widths ≥480px after implementation, check for a typo in the modifier class name or a missing class on the root div — not a specificity problem, since the math is unconditional.
