# Phase 03.1: Code Review Report

**Reviewed:** 2026-07-13T11:06:58Z
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

This phase wires the existing `MarkdownField` component (edit/preview toolbar, auto-grow textarea, container-query split view) into `SessionLog`'s "Quick Notes" panel, and adds a `forceTabs` opt-in to keep that panel single-pane regardless of container width. The actual diff for this phase is small (a `forceTabs` prop + 3 CSS override rules + swapping a plain `<textarea>` for `<MarkdownField>`), but reviewing the full files surfaced a concrete, reproducible rendering bug caused by the new wiring (missing `key` prop, unlike its sibling `RichTextEditor`), a pre-existing state/CSS desync in the shared component that this phase's new consumer inherits, a markdown-preview styling gap (GFM tables render unstyled), and a stale/misleading UI hint. No security issues or crashes were found; `ReactMarkdown` is used without `rehype-raw`, so no injected HTML/XSS surface exists here.

For context, the component's supporting modules (`MarkdownPreview.jsx`, `markdownToolbar.js`) and a couple of call sites (`Toolkit.jsx`, `App.jsx`) were read to verify call-chain behavior, per adversarial-review practice, even though they are not part of the file list under review.

## Warnings

### WR-01: Quick Notes textarea can visually collapse to 0px height after switching sessions

**File:** `src/client/components/tabs/SessionLog.jsx:193-198`
**Issue:** The neighboring rich-text editor is explicitly remounted per session (`<RichTextEditor key={session.id} ... />`, line 147), but the new `<MarkdownField>` for Quick Notes has no `key` at all:

```jsx
<MarkdownField
  value={session.sessionNotes}
  onChange={v => updateNotes(v)}
  forceTabs
  placeholder="Quick notes, reminders, DC results..."
/>
```

Because `MarkdownField` isn't remounted on session switch, its internal `activeTab` state (`'edit' | 'preview'`) survives across sessions. If the DM leaves session A's Quick Notes on the **Preview** tab and then switches to session B (via the sidebar) without changing tabs, `MarkdownField` receives session B's `sessionNotes` as a new `value` while the textarea is still `display: none` (forced by `forceTabs` + `activeTab === 'preview'`).

`useAutoGrow` (`MarkdownField.jsx:7-16`) reacts to that `value` change with:
```js
el.style.height = 'auto'
el.style.height = `${el.scrollHeight}px`
```
`scrollHeight` of a `display: none` element is always `0`, so the textarea's inline height gets pinned to `0px`. Because the effect only re-runs when `value` changes (not when `activeTab` changes), switching back to the "Edit" tab does not recompute the height — the textarea reappears with `height: 0` (and, since `box-sizing: border-box` is applied globally, the 12px padding is squeezed out too), making session B's notes appear to have vanished even though the underlying value is intact in the DOM.
**Fix:** Give `MarkdownField` the same session-scoped key as `RichTextEditor`, and/or make `useAutoGrow` visibility-aware:
```jsx
<MarkdownField
  key={session.id}
  value={session.sessionNotes}
  onChange={v => updateNotes(v)}
  forceTabs
  placeholder="Quick notes, reminders, DC results..."
/>
```
```js
// MarkdownField.jsx — guard against measuring a hidden element
useLayoutEffect(() => {
  const el = ref.current
  if (!el || el.offsetParent === null) return
  el.style.height = 'auto'
  el.style.height = `${el.scrollHeight}px`
}, [value])
```

### WR-02: Formatting toolbar can get stuck disabled when the container crosses the responsive breakpoint

**File:** `src/client/components/markdown/MarkdownField.jsx:19-21`, `src/client/index.css:81-85`
**Issue:** `toolbarDisabled = activeTab !== 'edit'` assumes the textarea is only visible when `activeTab === 'edit'`. That's true for `forceTabs` consumers and for narrow containers, but for the default (non-`forceTabs`) consumers — `SessionPrep`, `Locations`, `CharacterModal`, etc. — the `@container mdfield (min-width: 480px)` rule forces **both** panes visible side-by-side regardless of `activeTab`:
```css
@container mdfield (min-width: 480px) {
  .markdown-field-body { display: grid; grid-template-columns: 1fr 1fr; ... }
  .markdown-field-tabs { display: none; }
  .markdown-field-pane-hidden { display: block; }
}
```
Reachable sequence: on a narrow container, the tab buttons are visible, the DM clicks "Preview" (`activeTab` becomes `'preview'`), then widens the window/panel past 480px. The CSS now shows the edit textarea again (split view), but `toolbarDisabled` is still `true` because `activeTab` never changed back — Bold/Italic/Heading/Bullet stay disabled even though the textarea is visible and editable, until the (now-hidden, since tabs are `display:none` in split view) tab buttons are somehow clicked again, which the user can no longer do without shrinking the window back down.
**Fix:** Disable the toolbar based on actual pane visibility rather than raw tab state, e.g. track a `isSplitView` via a `ResizeObserver`/container query match, or simply always enable the toolbar and let CSS `pointer-events` handle the truly-hidden case.

### WR-03: `remarkGfm` tables render with no visual styling

**File:** `src/client/index.css:49-61`, `src/client/components/markdown/MarkdownPreview.jsx:16`
**Issue:** `MarkdownPreview` enables `remarkGfm`, which parses GitHub-flavored tables, but `.markdown-preview` in `index.css` only styles `h1-h3`, `p`, `ul`, `ol`, `li`, `strong`, `em`, `blockquote`, `code`, and `pre`. There are no `table`, `thead`, `th`, or `td` rules. Any Quick Notes (or other markdown field) content that includes a GFM table will render with default browser table styling — no borders, no cell padding, uneven columns — which looks broken against this dark, custom-styled UI.
**Fix:**
```css
.markdown-preview table { width: 100%; border-collapse: collapse; margin: 8px 0; font-size: 14px; }
.markdown-preview th, .markdown-preview td { border: 1px solid #332922; padding: 6px 10px; text-align: left; }
.markdown-preview thead th { background: #211b17; color: #d4a574; }
```

### WR-04: Quick Notes hint text overstates what's captured automatically

**File:** `src/client/components/tabs/SessionLog.jsx:192`
**Issue:** The hint above the new `MarkdownField` reads:
```jsx
<p className="text-xs text-[#666] mb-2">DC button clicks are logged here automatically.</p>
```
Nothing in `Toolkit.jsx` (ability checks, dice rolls, loot generation, name generation, etc.) logs to Quick Notes automatically — every result requires the DM to explicitly click the "★ Save" button (`SaveBtn`, `Toolkit.jsx:100-126`). A DM relying on this hint's literal claim will lose rolls/results they assumed were being captured for them.
**Fix:** Update the copy to reflect the actual (manual) behavior, e.g. `"Click ★ Save on any Toolkit result to log it here."`

## Info

### IN-01: Quick Notes field has no accessible label

**File:** `src/client/components/tabs/SessionLog.jsx:191-198`, `src/client/components/markdown/MarkdownField.jsx:60-67`
**Issue:** The "Quick Notes" `<h2>` is visually adjacent to the field but not programmatically associated with the underlying `<textarea>` (no `htmlFor`/`id` pair, and `MarkdownField` doesn't accept an `aria-label` prop). Screen reader users get an unlabeled textarea.
**Fix:** Add an `aria-label` (or `aria-labelledby`) prop to `MarkdownField` and pass it from `SessionLog`: `<MarkdownField aria-label="Quick notes" ... />`, forwarding it to the internal `<textarea>`.

### IN-02: `forceTabs` CSS restates base rules verbatim instead of disabling the container query

**File:** `src/client/index.css:65-66, 79, 87-89`
**Issue:** The `forceTabs` override block:
```css
.markdown-field-force-tabs .markdown-field-tabs { display: flex; }
.markdown-field-force-tabs .markdown-field-body { display: flex; flex-direction: column; }
.markdown-field-force-tabs .markdown-field-pane-hidden { display: none; }
```
is identical to the pre-container-query base rules it's overriding (needed only to win specificity against the `@container` block). If the base single-column layout ever changes, this duplicate has to be updated in lockstep or it silently drifts.
**Fix:** Consider scoping the container query itself with `:not(.markdown-field-force-tabs)`, e.g. `@container mdfield (min-width: 480px) { .markdown-field:not(.markdown-field-force-tabs) .markdown-field-body { ... } }`, so there's a single source of truth for the "tabs" layout.

### IN-03: Heading levels 4-6 and `<hr>` fall back to unstyled browser defaults in markdown preview

**File:** `src/client/index.css:49-61`
**Issue:** Only `h1`, `h2`, `h3` get the amber-heading treatment. `h4-h6` and thematic breaks (`---`) produced by markdown will use default browser styling, which is visually inconsistent with the rest of the themed preview pane (and default `<hr>` color may look muddy against `#161310`).
**Fix:** Add minimal `h4`/`h5`/`h6`/`hr` rules consistent with the existing scale, e.g. `.markdown-preview hr { border-color: #332922; margin: 12px 0; }`.
