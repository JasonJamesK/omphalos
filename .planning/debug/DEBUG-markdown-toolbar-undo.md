## Evidence

  found: `setNativeTextareaValue(textarea, value)` gets the native `value` property descriptor's setter off `window.HTMLTextAreaElement.prototype`, calls it directly (`setter.call(textarea, value)`), then dispatches `new Event('input', { bubbles: true })`. Both `wrapSelection()` and `insertAtCursor()` (the only two toolbar-mutation functions, backing all 4 toolbar buttons: Bold, Italic, Heading, Bulleted-list) call this as their sole mutation path — no alternative code path exists.
  implication: This is the exact mechanism 02-RESEARCH.md Pattern 4 describes and the exact mechanism the symptom asks to be investigated.

- timestamp: 2026-07-12T13:42:00Z
  checked: `src/client/components/markdown/MarkdownField.jsx` (full file)
  found: The `<textarea>` is a standard React controlled component (`value={value || ''}`, `onChange={e => onChange(e.target.value)}`), no `onKeyDown`, no other event interception. Toolbar buttons call `wrapSelection(textareaRef, ...)` / `insertAtCursor(textareaRef, ...)` directly on click — these are the ONLY call sites of `setNativeTextareaValue` in the whole client codebase (confirmed via grep across `src/client`).
  implication: Every toolbar-triggered edit in every MarkdownField instance goes through the same single potentially-flawed mutation path; no toolbar button bypasses it, and no non-toolbar code path uses it (plain typing never calls `setNativeTextareaValue`).

- timestamp: 2026-07-12T13:50:00Z
  checked: WebSearch for "programmatically setting textarea value native setter dispatchEvent input breaks undo ctrl+z chrome"
  found: Multiple independent, authoritative sources confirm that programmatically assigning `.value` on an `<input>`/`<textarea>` — via ANY means, including the native property setter — clears/breaks the browser's native undo (Ctrl+Z) history for that field, because browsers track undo state via their real internal text-editing command pipeline (actual keystrokes, IME composition, cut/paste, drag/drop), not via the JS `'input'` DOM event. Key corroborating source: **Mozilla Bugzilla #1523270** — "Editable component (textarea) ctrl+z undo history lost after value property assignment" — a filed, acknowledged browser-engine-level bug/behavior report matching this exact scenario. A second source (xjavascript.com) explicitly states: "simply using `dispatchEvent('input')` after setting the value programmatically doesn't restore undo functionality — you need to use a method that actually simulates user input like `setRangeText()`" (or the deprecated `document.execCommand('insertText', ...)`, which DOES go through the real editing pipeline and IS undo-tracked).
  implication: 02-RESEARCH.md Pattern 4's stated rationale ("native setter + dispatchEvent preserves native undo") is factually incorrect. The native-setter trick solves a *different* problem — making REACT's controlled-component reconciliation recognize a programmatic value change so `onChange` fires and React state stays in sync (this is the well-known "React controls you" pattern used by testing-library/simulated-native-events, cited in the research doc itself via dev.to/poeticgeek/in-react-component-controls-you-4ed8). It does nothing to preserve the browser's own undo manager. The one deprecated API the research doc explicitly avoided (`document.execCommand('insertText', ...)`) — or its modern non-deprecated replacement, `textarea.setRangeText()` — is actually the mechanism that WOULD have preserved native undo, because both go through the browser's real text-editing command pipeline.

- timestamp: 2026-07-12T13:55:00Z
  checked: Whether the "doesn't do anything" wording is consistent with "history cleared" vs. "history preserved but reverts to wrong point"
  found: If the toolbar's `.value=` assignment simply cleared the undo stack at that point, the *typed* characters afterward (real keystrokes) should still build a fresh undo entry and Ctrl+Z should at minimum undo those typed characters (reverting to the post-toolbar, pre-typing state) — yet the user reports total inertness, not partial-undo-then-stop. This is consistent with the Firefox bug report's framing (undo history "lost", i.e. the field's undo manager is left in a state where it no longer responds to Ctrl+Z at all following a script-driven value assignment, not merely "one entry short") and is also consistent with Chromium's documented behavior of disabling native undo for a text field for the remainder of its session once `.value` has been set via script, until the field is reset (e.g., re-mounted or blurred+refocused in some engines) — exact browser-specific granularity (Chromium vs Firefox vs WebKit) does not change the root cause, only the precise failure texture.
  implication: The symptom's literal wording ("doesn't seem to do anything," not "undoes typing but stops at Bold") is fully explained by the confirmed mechanism — no separate/additional bug is needed to account for total inertness.

- timestamp: 2026-07-12T14:00:00Z
  checked: Whether this is (a) an app-wide bug affecting ALL edits (including plain typing with no toolbar), or (b) specific to the toolbar's implementation, per the symptom's explicit request to distinguish these
  found: Code-level: `setNativeTextareaValue` (the only value-clobbering codepath) is called EXCLUSIVELY from `wrapSelection`/`insertAtCursor`, which are EXCLUSIVELY wired to the 4 toolbar buttons. Plain typing goes through React's normal controlled-input flow (`onChange={e => onChange(e.target.value)}`) — the DOM's real `input` event fires natively from the actual keystroke, React's textarea `updateWrapper` reconciliation skips reassigning `node.value` when it already equals the next computed prop value (which it does here, since `onChange` passes the raw `e.target.value` straight through with no transformation before it round-trips back as `value`), so no programmatic `.value=` write ever happens for plain typing. Plain typing (real keyboard) should therefore preserve native undo correctly in a real browser — this is answer (b): the bug is specific to the toolbar's implementation, not a symptom of all edits in the field being broken.

## Resolution

root_cause: >
  `markdownToolbar.js`'s `setNativeTextareaValue()` — used by every toolbar button (Bold/Italic/Heading/Bulleted-list) via `wrapSelection()`/`insertAtCursor()` — sets the textarea's `.value` via the native `HTMLTextAreaElement.prototype.value` property setter and then dispatches a synthetic `input` event. This pattern correctly solves the problem of making React's controlled-component reconciliation recognize a programmatic value change (so `onChange` fires and React state stays in sync) — but it does NOT preserve the browser's native undo (Ctrl+Z) stack, contrary to the explicit rationale documented in 02-RESEARCH.md Pattern 4/Pitfall 1 and locked in CONTEXT.md D-08. Browsers track native undo history via their real internal text-editing command pipeline (actual keystrokes, IME composition, cut/paste, drag/drop, or `document.execCommand`) — NOT via the `'input'` DOM event, which is purely a JS-observable notification. Any script-driven `.value` assignment — even through the native property setter — clears/breaks the field's undo history (corroborated by Mozilla Bugzilla #1523270, "ctrl+z undo history lost after value property assignment", and multiple independent sources confirming `dispatchEvent('input')` does not restore undo functionality; only `textarea.setRangeText()` or the deprecated `document.execCommand('insertText', ...)` go through the browser's real editing pipeline and are undo-tracked). This is specific to toolbar-triggered mutations only — plain typing (real keystrokes) never touches `setNativeTextareaValue` and follows React's normal controlled-input flow, which does not force a redundant `.value` write (React's textarea reconciliation skips the write when `node.value` already equals the next prop value, which it does after a real keystroke since `onChange` passes `e.target.value` straight through unmodified).
